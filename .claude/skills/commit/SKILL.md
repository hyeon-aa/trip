# /commit — 컨벤션에 맞는 커밋

`docs/CONVENTIONS.md`에 정리된 형식을 따른다:
```
<type>: <설명>(<scope>)
```

## 1. 현재 상태 파악

```bash
git status --porcelain
git diff
git diff --staged
```
스테이징된 게 없으면 무엇을 커밋할지(전체 vs 일부) 사용자에게 확인한다.

**diff가 서로 다른 관심사(기능)를 여러 개 담고 있으면, 하나로 뭉치지 말고
기능별로 나눠서 커밋하는 걸 기본으로 고려한다** — 예를 들어 "핵심 기능 +
그 과정에서 나온 리팩터링 + 별개의 버그 수정 + 성능 개선"처럼 성격이 다른
변경이 섞여 있으면, 각각 독립된 커밋으로 나누는 게 나중에 `git log`/`git
blame`으로 이력을 추적하기 쉽다. 반대로 처음부터 하나의 응집된 기능으로
설계·구현된 diff(예: 새 인프라 하나를 통째로 추가)라면 굳이 인위적으로
쪼갤 필요 없다 — 애매하면 사용자에게 "기능별로 나눌까요, 하나로 묶을까요"
짧게 물어본다.

나누기로 했다면:
1. diff를 훑어서 논리적 경계(핵심 기능 / 파생된 리팩터링 / 별개 버그 수정 /
   문서)를 먼저 정하고, 각 경계에 어떤 파일·어떤 부분이 속하는지 정리한다.
2. **파일 하나에 여러 커밋 몫의 변경이 섞여 있으면(가장 흔한 경우 — 컨트롤러
   하나에 여러 기능이 같이 얹힘), 단순히 hunk를 나눠서 스테이징하는 것만으로는
   안 된다** — 그러면 중간 커밋 시점에 파일이 반쯤 적용된 상태가 돼서 컴파일이
   안 될 수 있다. 대신 `git show HEAD:<path>`로 원본을 떠서, 각 커밋 몫만큼만
   반영된 중간 버전을 실제로 만들어(다음 커밋 몫은 아직 원래 상태로 되돌려놓고)
   그 상태로 컴파일/테스트가 통과하는지 확인한 뒤 커밋하고, 다음 커밋으로
   넘어간다. 마지막 커밋에서 최종(현재) 상태로 돌아온다.
3. **각 커밋 이후 상태가 실제로 빌드되는지 확인한다** — 최소
   `./gradlew compileJava`(서버) / 관련 빌드 명령을 각 커밋 직후 실제로
   실행해서 확인. "논리적으로는 나뉘는데 중간 상태가 깨진 커밋"은 나눈
   의미가 없다.
4. 커밋마다 메시지도 그 부분만의 "왜"를 담아 따로 쓴다 — 뭉뚱그린 메시지
   하나를 재사용하지 않는다.

## 2. type 결정

diff 내용을 보고 판단:
- `feat` — 새 기능/코드 추가
- `fix` — 버그 수정
- `chore` — 설정, 의존성, 잡일성 변경
- `refactor` — 동작 변화 없는 구조 개선

## 3. scope 결정

변경된 파일이:
- `client/` 아래만 → `(front)`
- `server/` 아래만 → `(back)`
- 둘 다 걸치거나 루트 설정/문서면 → scope 생략

## 4. 설명 작성

한글로, diff의 "무엇을 왜 바꿨는지" 핵심만 간결하게. 기존 커밋 예시
(`git log --oneline -10`)와 톤을 맞춘다.

## 5. 초안 확인 + 커밋

작성한 메시지를 사용자에게 보여주고 확정되면 스테이징 후 커밋한다:
```bash
git add <files>
git commit -m "$(cat <<'EOF'
<type>: <설명>(<scope>)

Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
EOF
)"
```
사용자가 별도 커밋 메시지를 이미 준 경우 그대로 쓰고, 컨벤션에서 벗어나면
한 번 확인만 하고 사용자가 원하는 대로 진행한다.
