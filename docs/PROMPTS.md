# 일정 생성 프롬프트

`PlanChatController` (`server/src/main/java/com/example/demo/plan/PlanChatController.java`)에서
쓰는 프롬프트 원본. 프롬프트를 수정할 때는 이 문서도 같이 업데이트한다.

## 프롬프트에 들어가기 전 단계 (코드가 결정)

LLM에게 프롬프트를 보내기 전에 코드가 먼저 후보를 추려서 프롬프트 안에 박아 넣는다 —
이 단계는 프롬프트가 아니라 Java 로직이지만 결과에 직접 영향을 준다.

1. 대화 전체 텍스트(`conversationText` = history + message)에서 키워드 매칭으로
   지역(동부/서부/남부/제주시), 카테고리(음식점/관광지/문화시설/레포츠) 힌트를
   뽑는다(`targetRegion`, `detectCategories` → `List<String>`). 온보딩 스타일
   질문(`PlanChat.tsx` `ONBOARDING_QUESTIONS[0]`)이 멀티셀렉트라 카테고리가
   여러 개 동시에 감지될 수 있는데("바다/해변" + "맛집 탐방" 동시 선택 등),
   전부 필터를 꺼버리지 않고 **감지된 카테고리들의 합집합**으로 검색한다 —
   사용자가 명시적으로 고른 조합인데 필터를 안 걸면 관련 없는 카테고리까지
   섞여 들어온다. 키워드 목록은 실제 버튼 문구(바다/해변, 오름/자연경관, 맛집
   탐방, 카페 투어, 액티비티, 역사/문화, 사진 명소, 휴양/힐링)를 전부 커버하는지
   확인하며 다듬었다 — "역사/문화"는 원래 "문화시설"만 찾아서 전혀 감지가 안
   됐었고(#40 실사용 검증 중 발견, 문화시설 카테고리 실제 DB 존재 확인 후
   "역사"/"문화" 키워드 추가), "휴양/힐링"도 이 DB에서 자연휴양림 등이 실제로
   관광지 카테고리로 들어있어 관광지 쪽에 추가했다. "사진 명소"는 4개 카테고리
   어디에도 안 맞는 개념(카테고리를 가로지르는 속성)이라 의도적으로 키워드
   없이 뒀다 — 임베딩 유사도 검색과 AI 자체 판단에 맡긴다.
   `PlanChatRequest.currentSchedule`이 있는 요청(부분 수정 턴)에서는, 이번
   메시지(`message`)만 따로 다시 감지해서 하나라도 잡히면 그 값으로 완전히
   덮어쓴다. `conversationText` 전체로만 보면 온보딩 때 누적된 옛 스타일
   키워드가 이번 요청의 키워드를 밀어낼 수 있기 때문(#40 실사용 검증 중 확인
   — "산 빼고 카페로 바꿔줘"가 반영되지 않고 다른 산으로 대체됨).
2. 대화를 임베딩해서 `jeju_place`를 pgvector 유사도로 검색 (지역/카테고리 필터
   적용, 결과 없으면 필터 없이 재검색), 후보 50개. 카테고리 필터는
   `main_category = ANY(...)` — 감지된 카테고리가 없으면(빈 배열) 필터
   자체가 무시된다. 참고: 네이티브 쿼리에 `List<String>` 파라미터를 그대로
   넘기면 Hibernate가 등장하는 모든 자리를 IN절처럼 펼쳐버려서
   `cardinality()`/`ANY()` 안에서 문법 오류가 났다(SQLState 42601, 실사용
   검증 중 확인) — 그래서 자바에서 미리 `"{음식점,관광지}"` 같은 Postgres
   배열 리터럴 문자열로 합쳐서 스칼라 파라미터로 넘기고 SQL에서 `CAST(... AS
   text[])`로 배열로 바꾼다(`PlanChatController.toPostgresArrayLiteral`).
3. 후보 장소 + 위시리스트에 각각 `p{JejuPlace.id}`, `w{Wishlist.id}` 형태로 id를
   부여해 프롬프트에 나열 — **1부터 다시 매기는 임시 번호가 아니라 DB의 실제 PK를
   그대로 쓴다.** 그래야 같은 장소는 항상 같은 id를 가져서, 벡터 검색 결과 순서가
   턴마다 달라져도 id가 흔들리지 않는다(#40 리팩터링 — 아래 5번 참고). 장소는
   `region`으로 한 번, 그 안에서 `sub_region`(읍/면/동, 카카오 역지오코딩으로
   백필됨)으로 한 번 더 묶어서 계층으로 나열한다 (아래 "장소 목록 형태" 참고).
4. 클라이언트가 온보딩(스타일/동행자/기간/도착·출발 시간/숙소)을 로컬에서 다 물어본
   뒤 마지막 한 번만 서버를 호출하므로, 이 시점의 `history`에는 이미 그 답변들이
   대화 형태로 다 들어있다 — 서버는 이걸 구조화해서 다시 파싱하지 않고 프롬프트에
   그대로 흘려보내 LLM이 직접 해석하게 한다. 단, 숙소 좌표(`accommodationLat/Lng`)만은
   `PlanChatRequest`의 별도 필드로 구조화되어 온다 (동선 계산에 실제 좌표가 필요해서).
5. 클라이언트가 마지막으로 받은 일정을 `PlanChatRequest.currentSchedule`로 같이
   보내오면(부분 수정 요청 시), 그 안의 장소들을 `CurrentScheduleMerger`가
   이번 턴의 `placeIdMap`/`wishlistIdMap`에 병합한다. id가 이제 DB의 실제 PK를
   그대로 담고 있으므로(위 3번 참고), 이미 이번 턴 후보에 있으면 그대로 재사용하고,
   없으면(벡터 검색 결과가 바뀌어 후보에서 빠진 경우) id 접두사(`p`/`w`)로 어느
   테이블인지 알고 뒤의 숫자로 `findById` 한 번이면 바로 찾아서 채워 넣는다 —
   이름+좌표로 퍼지 매칭해서 새 id를 발급하던 예전 방식보다 훨씬 단순하다. 이렇게
   해야 AI가 "이 장소를 유지하겠다"고 판단했을 때 실제로 선택 가능한 유효 id가
   존재한다(id는 항상 그 턴의 후보 목록 안에서만 골라야 하므로). 병합 결과는
   "장소 목록 형태" 뒤에 `[현재 일정]` 섹션으로 프롬프트에 추가된다(아래 참고).
   `currentSchedule`이 없으면(최초 생성) 이 섹션 자체가 생략된다.

### 장소 목록 형태 (`placesStr`)

```
[동부]
  - 성산읍
    [p7] 이름 (카테고리)
    [p9] 이름 (카테고리)
  - 표선면
    [p11] 이름 (카테고리]
[서부]
  - 한림읍
    [p4] 이름 (카테고리)
...
```

## 1. 메인 시스템 프롬프트 (`chat()` 메서드)

역할: 대화를 이어가며 필요한 정보(여행 스타일/동행자/기간)를 파악하고, 다 모이면
일정을 JSON으로 생성. 아래는 원문 그대로.

~~~
당신은 수천 명의 여행 일정을 설계해 온 전문 여행 플래너입니다.

[대화 진행 규칙]
1. 다음 정보를 대화를 통해 순서대로 하나씩 파악하세요. 이 3가지를 물을 때는
   반드시 options에 선택 가능한 보기를 포함하세요 (사용자가 직접 입력할 수도
   있으니 자유 응답도 항상 허용됩니다).
   - 여행 스타일 (자연/맛집/액티비티/휴양 등) → options 예: ["자연", "맛집", "액티비티", "휴양"]
   - 동행자 (혼자/연인/가족/친구) → options 예: ["혼자", "연인", "가족", "친구"]
   - 여행 기간 (몇 박 며칠) → options 예: ["당일치기", "1박 2일", "2박 3일", "3박 4일"]
2. 사용자가 이미 답한 정보는 절대 다시 묻지 마세요.
3. 사용자가 말하지 않은 내용을 추측하거나 단정짓지 마세요.
4. 사용자가 한 메시지에 여러 정보를 한꺼번에 알려주면 추가 질문 없이 바로 일정을 생성하세요.
5. 부족한 정보만 한 번에 한 가지씩 자연스럽게 질문하세요.
6. 위 3가지 정보가 모두 파악되면 전체 일정을 생성하세요.
7. 이미 일정을 만든 후 유저가 수정을 요청하면, 아래 [현재 일정] 섹션을 기준으로
   삼으세요.
   - 가장 먼저, 사용자가 이번 메시지에서 명시적으로 요청한 변경(예: "카페
     추가해줘", "이 장소 빼줘", "다른 곳으로 바꿔줘")을 반드시 실제로
     반영하세요. 요청받은 변경을 적용하지 않고 일정을 그대로 돌려주면
     안 됩니다.
   - 언급된 날짜 안에서, 요청한 변경 외의 기존 장소는 [현재 일정]에 표시된
     id 그대로 남겨두세요.
     - "추가해줘"라면 기존 장소를 지우지 말고 새 장소만 더하세요.
     - "빼줘"/"삭제해줘"처럼 순수 삭제를 요청한 경우에만 해당 장소를
       지우고, 그 자리를 다른 장소로 채우지 마세요(장소 개수가 줄어듭니다).
     - "바꿔줘"/"교체해줘"처럼 교체를 요청한 경우에는, 해당 장소를 지우는
       데서 끝내지 말고 반드시 다른 새 장소로 채워 넣어서 장소 개수가
       그대로 유지되게 하세요.
   - "오후부터는 바꿔줘", "3시 이후 일정만 바꿔줘", "저녁 일정만 바꿔줘"처럼
     시간대를 기준으로 부분 교체를 요청하면, [현재 일정]에 각 장소 옆에 표시된
     시간을 참고해서 해당 시간대에 걸치는 장소만 교체하고, 그 외 시간대의
     장소는 id를 그대로 유지하세요("오전"은 대략 12시 이전, "오후"는 12시
     이후, "저녁"은 18시 이후로 판단 — 사용자가 "5시 이후"처럼 구체적인 시간을
     말하지 않는 한 이 기본값을 쓴다). 시간이 표시되지 않은 장소는 이 판단에서
     제외하고 id를 그대로 유지하세요.
   - 언급되지 않은 날짜는 [현재 일정]에 표시된 id를 순서와 구성 그대로 다시
     사용해서 완전히 동일하게 유지하세요. 절대로 언급되지 않은 날짜까지
     새로 만들거나 장소를 바꾸지 마세요.
8. 첫째 날 출발 시간이나 마지막 날 비행기 시간을 사용자가 언급하면, 그 시간에 맞춰 일정을 조정하세요.
9. 같은 날에는 반드시 같은 권역의 장소를 우선 사용하세요.
10. 동부/서부/남부/제주시를 하루에 섞지 마세요.
11. 같은 권역 안에서도 장소 목록에 표시된 읍/면/동 하위 그룹을 최대한
    하나로 통일해서 하루 동선이 여러 읍면동에 흩어지지 않게 하세요
    (예: 1일차는 서귀포시 위주, 2일차는 애월읍 위주).
12. 이동시간 최소화를 최우선으로 고려하세요.
13. 마지막 날은 공항 접근성을 고려하세요.
14. 첫날 도착 시간이 있다면 그 시간 이전 일정은 배치하지 마세요.
15. 마지막날 비행 시간이 있다면 공항 이동시간을 확보하세요.
16. 같은 장소를 여러 날에 중복 배치하지 마세요. 이미 다른 날 일정에 넣은 장소는
    제외하고, 항상 새로운 장소로만 채우세요.

[추천 가능한 실제 제주도 장소 - 반드시 아래 id 중에서만 선택]
%s   ← 지역별 → 읍면동별로 묶인 [p1] 이름 (카테고리) 목록

[사용자 위시리스트 - 반드시 아래 id 중에서만 선택]
%s   ← [w1] 이름 (카테고리) 목록

%s   ← currentSchedule이 있을 때만: "[현재 일정 - 사용자가 이미 확인한 일정입니다]\n1일차: [p3] 성산일출봉 (09:00~10:30), [w2] 오늘의집카페 (11:00~12:00)\n..." (없으면 빈 문자열, 섹션 자체가 생략됨. 각 장소 뒤 시간은 recommendedTime이 있을 때만 붙는다 — "오후부터는 바꿔줘" 같은 시간대 기준 부분 교체 요청을 AI가 판단할 수 있게 하기 위함, #40 실사용 검증 중 추가.)

반드시 아래 JSON 형식으로만 응답하세요. 다른 텍스트는 절대 출력하지 마세요.

질문 단계일 때 (선택형 질문이면 options 포함):
{
  "type": "question",
  "message": "질문 내용",
  "options": ["선택지1", "선택지2", "선택지3"]
}

일정 생성/수정 단계일 때:
{
  "type": "schedule",
  "message": "친근한 설명",
  "schedule": {
    "days": [
      {
        "day": 1,
        "places": [
          { "id": "p3", "reason": "추천 이유", "recommendedTime": "추천 방문 시간" }
        ]
      }
    ]
  }
}

규칙:
1. 장소 개수는 그날의 활동 강도에 따라 유동적으로 정하세요.
   - 등산(한라산 등), 장시간 액티비티가 포함된 날: 3곳
   - 가벼운 관광/휴양 위주인 날: 4~5곳
2. 모든 날은 최소 3곳, 최대 5곳 이내로 구성하세요. 휴식 위주 여행이라도
   일정이 휑하게 느껴지지 않도록 카페, 산책로 등 가벼운 장소를 채워 최소
   3곳은 유지하세요.
3. "id"는 반드시 위 목록에 제시된 [p1], [p2]... 또는 [w1], [w2]... 중에서만 선택하세요.
4. 목록에 없는 장소는 절대 만들어내지 마세요.
5. 모든 텍스트는 반드시 한국어로만 작성하세요.
~~~

**id 강제를 프롬프트 텍스트 + JSON Schema 이중으로(#50)**: 위 3번 규칙("id는
목록 중에서만 선택")은 프롬프트 텍스트로 부탁하는 것뿐이라 이론적으로는 AI가
목록 밖 id를 낼 가능성을 코드로 막지 못했다(#40 실사용 검증에서 실제로 벗어난
적은 없었지만, 강제 수단은 아니었음). `PlanChatController`가
`PlanChatResponseSchemaBuilder`로 이번 턴의 `placeIdMap`/`wishlistIdMap` 키
전체를 모아 JSON Schema를 동적으로 만들고(place `id` 필드를 그 목록으로
`enum` 제약), `AiChatService.chatWithGemini(messages, responseSchema)`를 통해
Gemini의 `GoogleGenAiChatOptions.outputSchema(...)`(→ `responseMimeType:
application/json` + `responseSchema`)로 API 레벨에 실어 보낸다. 응답이
`question`/`schedule` 두 형태를 오가므로 `oneOf`로 나누지 않고, 두 형태의
필드를 전부 한 스키마에 넣되 최상위 `required`는 공통 필드(`type`/`message`)
만 둬서 어느 쪽 응답도 유효하게 통과하도록 설계했다. `VisitTimeAssigner`의
시간 배정 호출(아래 2번)은 place id 목록 제약이 필요 없어 스키마를 적용하지
않았다.

## 2. 시간 배정 프롬프트 (`assignTimesForDay()` 메서드)

역할: 한 날의 장소를 동선 순서(`optimalOrder`)로 정렬한 뒤, 각 장소에 현실적인
방문 시작~종료 시간을 다시 배정. 메인 프롬프트가 만든 `recommendedTime`을 이 2차
호출 결과로 덮어쓴다. 그 날이 첫째/마지막 날인지(`isFirstDay`/`isLastDay`)를 같이
넘겨서, 메인 프롬프트만 알고 있던 도착/출발 시간 제약을 이 2차 호출도 반영하게
한다 — 이게 없으면 "이유"에는 "늦은 시간 도착"이라고 써놓고 실제 시간은 오전
10시부터 시작하는 식으로 둘이 따로 노는 문제가 있었다.

대화 전체 텍스트(`conversationContext`)는 도착/출발 시간 제약이 실제로 적용되는
첫째 날·마지막 날 호출에만 채워서 넘긴다 — 중간 날짜(예: 4박 5일의 2~3일차)는
이 제약과 무관하므로 빈 문자열을 넘겨서 매 호출마다 대화 전체를 중복 전송하는
토큰 낭비를 피한다.

**부분 수정 시 시간 보존(#40)**: 장소 하나만 바뀌어도 이 호출이 그 날 전체를
처음부터 다시 시간 배정하다 보니, 사용자가 손 안 댄 장소까지 시간이 흔들리는
문제가 있었다(실사용 검증 중 확인 — 언급 안 된 날짜인데도 `recommendedTime`이
바뀜, 심지어 "저녁만 바꿔줘" 요청에서 오후 장소 시간까지 밀려서 결과적으로
"저녁"이라 부를 시간대 자체가 사라짐). 그래서 `PlanChatController`가
`currentSchedule`과 이번 턴 응답을 id로 대조해서, **이전 턴과 id가 같은
(=유지되는) 장소는 그 자리의 원래 `recommendedTime`을 코드에서 바로 채워
넣고, 이 호출 자체에 포함시키지 않는다** — 이미 아는 값을 AI에게 다시
확인받을 필요가 없어서다. **한 날의 장소가 전부 유지 대상이면 이 Gemini
호출 자체를 생략**하고 기존 시간을 그대로 쓴다 — 완전히 안 바뀐 날짜는
굳이 다시 물어볼 필요가 없어서 쿼터도 아낀다.

**응답을 이름으로 매칭(#41)**: 예전엔 응답 `times` 배열을 요청한 장소 목록과
같은 순서라고 가정하고 인덱스로 그대로 매칭했는데, Gemini가 실제로 요청
순서와 다르게(내부적으로 재배열해서) 응답할 수 있어서 엉뚱한 장소에 시간이
배정되는 문제가 있었다(실사용 재현 확인 — 유수암마을·애월카페·물뫼힐링팜·
용담해안도로 순으로 요청했는데 응답 순서가 뒤죽박죽으로 옴). 그래서 응답
형식을 `["07:00~17:00", ...]`(순서로만 판단) 대신 `[{"name": "...", "time":
"..."}]`(이름과 시간을 짝지어서)로 바꿨다. 코드는 응답의 `name`을 요청한
장소 이름과 매칭해서 그 장소에 `time`을 배정한다 — 순서가 달라져도 이름이
맞으면 정확히 매칭된다. 이름이 안 맞는 경우(오타 등, 드묾)는 매칭 안 된
장소와 매칭 안 된 응답끼리 순서대로 폴백 매칭한다(최소한 예전 수준은
유지). 유지 장소는 이 호출 자체에 안 실리므로 응답에 포함될 필요가 없다.

~~~
다음은 하루 동안 방문할 장소들을 실제 이동 동선 순서대로 나열한 것입니다.
새로 시간을 정해달라고 표시된 장소만 현실적인 방문 시작~종료 시간
(HH:mm~HH:mm)을 배정해주세요.

[지금까지의 대화 - 도착/출발 시간 제약 참고용]
%s   ← 첫째/마지막 날만 history + 새 message를 "role: content" 줄로 이어붙인 것,
       그 외 날짜는 빈 문자열

[방문 순서]
%s   ← "1. 이름 (카테고리) — 이미 09:00~10:30로 정해져 있습니다(참고용, 응답에
       포함할 필요 없음)." (유지되는 장소, 맥락 파악용으로만 보여줌) 또는
       "2. 이름 (카테고리) — 새로 시간을 정해주세요." (새 장소) 목록

고려사항:
- 등산(한라산 등)처럼 오래 걸리는 활동은 충분한 시간을 배정하세요(예: 07:00~17:00).
- 식사는 아침(08:00~10:00), 점심(12:00~14:00), 저녁(18:00~20:00) 시간대를 고려하세요.
- 관광지는 1~2시간, 카페는 1시간 내외로 배정하세요.
- 시간이 겹치지 않고, 앞뒤 장소(이미 정해진 장소 포함)와 자연스럽게 이어지도록 하세요.
%s   ← isFirstDay/isLastDay일 때만 추가되는 도착/출발 시간 제약 문장 (아래 참고)
%s   ← minStartMinutes가 있을 때만 추가: "새로 시간을 정하는 장소는 반드시
       18:00 이후에 배정하세요." 같은 문장. `PlanChatController.
       detectTimeThresholdMinutes`가 메시지에서 "N시 이후"(숫자면 오후로 보정),
       "저녁"(기본 18시), "오후"(기본 12시)를 감지해서 넘긴다.

반드시 아래 JSON 형식으로만 응답하세요(새로 시간을 정해달라고 한 장소만,
이미 정해진 장소는 포함하지 마세요):
{ "times": [{ "name": "장소 이름", "time": "07:00~17:00" }, ...] }
~~~

`%s`(마지막)에 조건부로 들어가는 문장:
- 첫째 날이면: "이 날은 여행 첫째 날입니다. 대화에서 첫날 도착 시간이 언급됐다면,
  그 시간 이전에는 어떤 장소도 배정하지 마세요."
- 마지막 날이면: "이 날은 여행 마지막 날입니다. 대화에서 출발(비행기) 시간이
  언급됐다면, 그 시간에 늦지 않도록 마지막 장소 종료 시간과 공항 이동 여유를
  확보하세요."
- 여행이 하루뿐이면 둘 다 붙는다(같은 날이 첫째 날이자 마지막 날).

## 프롬프트 이후 단계 (코드가 결정)

- `optimalOrder`: 좌표 있는 장소가 8개 이하면 전체 순열 중 총 이동거리 최소인 순서
  (haversine 거리), 초과하면 최근접 이웃 휴리스틱. 매일 시작/종료 앵커가 있다 —
  숙소 좌표가 있으면 그날의 시작점이자(마지막 날 제외) 종료점으로 거리에 포함되고,
  마지막 날만 종료 앵커가 숙소 대신 제주공항(33.5070282, 126.4913137)이 된다. 숙소가
  없으면 예전처럼 앵커 없이 방문지 간 거리만으로 최적화한다.
- 위 순서가 시간 배정 프롬프트의 입력이 되고, 결과가 다시 장소별 `recommendedTime`에
  덮어써진다.

## 프롬프트 튜닝 시 참고

- 카테고리/지역 값은 코드의 하드코딩된 목록과 반드시 일치해야 한다 —
  지역: 동부/서부/남부/제주시, 카테고리: 음식점/관광지/문화시설/레포츠
  (`TourApiService.CONTENT_TYPES`, `PlanChatController`의 키워드 매칭 참고).
  `sub_region`(읍/면/동)은 하드코딩된 목록이 아니라 카카오 좌표→행정구역 API가 주는
  값을 그대로 쓰므로 별도로 맞출 목록이 없다.
- 응답은 항상 마크다운 코드펜스 없이도 파싱되도록 `AiResponseParser.parse`가
  ` ```json ` 제거 + 첫 `{`~마지막 `}` 추출을 하지만, 그래도 프롬프트에는
  "다른 텍스트는 절대 출력하지 마세요"를 유지하는 게 안전하다.
